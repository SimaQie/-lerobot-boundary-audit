# RTX 4090 / TorchCodec GPU decode validation — 2026-10-20

Research preview, not a stable GPU-reader release. The default audit path stays
CPU-only. This report separates three claims:

1. the existing CPU workflow runs on an RTX 4090 host;
2. TorchCodec can be made to decode on NVDEC and return tensors on CUDA;
3. GPU decoding has a measured benefit without hiding correctness limits.

Evidence is under `research/results/rtx4090/session-001/`. No real videos,
Parquet tables, derived real datasets, virtual environments or credentials are
included.

## 2. Phase A — existing CPU workflow

Tested commit `5da5384` for conformance, `4aee263` for AgiBot and `d1eb625`
for ALOHA/sampling; each summary records the actual commit and environment.

- `pytest`: 115 passed at the final branch tip (106 baseline tests plus 9 new
  environment/metrics tests).
- `ruff`: all checks passed on `src tests examples research/...`.
- Original fixture conformance: **208/208** checks matched their expected
  outcome (13 cases × 2 backends × 8 read modes). Deliberately faulty cases are
  expected to fail; the suite PASS includes that detection.
- AgiBot: baseline storage/decode pass; official PyAV and TorchCodec 60/60
  queries pass; full-loader probes 31 match / 5 undetermined per backend;
  sequential PyAV PTS reference 23,658/23,658 frames with 0 grid error;
  authored one-frame offset localized to episode 5, repair verified, official
  recheck pass, exact restore and unchanged source.
- ALOHA: 300/300 official queries pass per backend; probes 12 match / 24
  undetermined per backend (repeated real frames are the expected cause);
  20,000/20,000 PTS reference frames; offset localized to episode 25; repair
  verified and exactly restored; source unchanged.
- Mixed/stratified sampling reproduced the historical numbers exactly:
  AgiBot 31/5 and 35/1; ALOHA 12/24 and 29/7 for both backends. Status is
  `completed_with_ambiguity`, not a forced PASS. No errors, no missing slots.

Both real-data summaries are `expected_outcomes_met`; index corruption was
rejected and repair blocked as designed.

## 3. Phase B — CUDA build, stock CPU reader

The same sampling and conformance were rerun with `.consumer-gpu`:

- mixed/stratified counts are identical to Phase A for all 8 combinations;
- 78/78 conformance checks (13 cases × 2 backends × single/window/workers)
  matched expectations;
- probe versions record `torch=2.10.0+cu128`, `torchcodec=0.10.0+cu128`,
  `torch_cuda_available=true`, `torch_device_name=NVIDIA GeForce RTX 4090`,
  but `requested_decode_device=cpu`, `observed_decode_device=cpu`,
  `observed_output_device=cpu`, `cpu_fallback_observed=false`.

Inspection of the installed LeRobot 0.6.1 `VideoDecoderCache` confirms that it
constructs `VideoDecoder(file_handle, seek_mode="approximate")` with no device
argument. A CUDA build of the libraries therefore does **not** mean the stock
reader decodes on the GPU.

## 4. Phase C — explicit NVDEC

### 4.1 Smoke and capability

`VideoDecoder(path, device="cuda", seek_mode="exact").get_frames_at([0,1,2])`
returned `cuda:0` tensors for both AV1 samples (shape `3×3×H×W`, uint8,
PTS 0/0.02/0.04 and 0/0.0333/0.0667). `cpu_fallback` reported "No fallback
required". FFmpeg listed all cuvid decoders; direct `ffmpeg -hwaccel cuda`
decoded both files without errors. This is an explicit CUDA decode call, not
CPU decode followed by `.to("cuda")`.

### 4.2 Correctness matrix

The independent tool is `research/benchmark_gpu_decode.py`. It decodes CPU
TorchCodec and CUDA TorchCodec in the same CUDA consumer, builds a sequential
PyAV ordinal reference as a second reference, compares requested ordinals
first/last/±1 and every episode seam ±1, repeats some indices, and tests both
`exact` and `approximate` time seeks including the exclusive file end.

Fixture identity is decoded from the original marker/CRC oracle, not from MP4
timestamps. CUDA and CPU behave identically on the controls:

| Fixture | Expected | CPU result | CUDA result |
|---|---|---|---|
| clean | all identities valid | pass | pass |
| duplicate pixel frame | frame 8 must not pass | 3 detections | 3 detections |
| camera swap | wrong camera | 14 detections | 14 detections |
| pixel-order swap | frames 8/9 exchanged | 6 detections | 6 detections |

A faulty frame never became a PASS; unknown marker identity is reported
separately and is not counted as a detection.

Real AV1 results (156 ordinal + 10 time checks for ALOHA; 36 + 10 for AgiBot):

| Input/device | pass | ambiguous | expected end-boundary error | wrong frame |
|---|---:|---:|---:|---:|
| ALOHA CPU | 89 | 75 | 2 | 0 |
| ALOHA CUDA | 52 | 112 | 2 | 0 |
| AgiBot CPU | 38 | 6 | 2 | 0 |
| AgiBot CUDA | 4 | 40 | 2 | 0 |

All valid requests had zero PTS error. The CUDA ambiguity increase is a
measurement result, not a threshold adjustment: CUDA RGB differs from CPU RGB
even after the range correction, so repeated/nearly repeated real frames are
harder to separate. There is no evidence of a wrong CUDA frame in this matrix,
but many GPU identities remain unverified.

### 4.3 Colour conversion finding

Both samples are AV1 Main, `yuv420p`, `color_range=tv`, with unspecified colour
matrix/transfer/primaries. CPU TorchCodec/PyAV returned full-range-looking RGB;
CUDA output was compressed toward TV range.

| Input/device | exact equals | raw RGB MAE median | max | TV→full adjusted MAE median | max |
|---|---:|---:|---:|---:|---:|
| ALOHA CPU | 89/166 | 0 | 0 | — | — |
| ALOHA CUDA | 0/166 | 9.747 | 10.431 | 0.633 | 0.734 |
| AgiBot CPU | 38/46 | 0 | 0 | — | — |
| AgiBot CUDA | 0/46 | 8.739 | 10.276 | 2.496 | 2.601 |

The existing heuristic (MAE ≤ 2 with ≥ 0.25 neighbour separation) is reported
unchanged. Raw CUDA output fails it; the documented limited-to-full adjustment
brings ALOHA below it but not AgiBot. For fixture identity the CRC markers are
used directly, so their PASS is not based on this RGB heuristic. No pixel
values are included in the public evidence.

### 4.4 Performance

32 distinct frames per request, one camera, decoder reused, 3 warm-ups and 5
timed repetitions per configuration, wall clock with CUDA synchronization.
"CPU end-to-end" includes decode + H2D to the common CUDA endpoint + a GPU
checksum; "CUDA end-to-end" includes decode + checksum. This is a
**single-video decoder microbenchmark**, not a full audit: it excludes reference
validation, LeRobot windows/actions/padding, the second camera and DataLoader
work, and it does not establish RGB-equivalent output. The limited-to-full
correction is not applied to the timing path. No OS page-cache clearing; CPU and
GPU groups ran sequentially. Medians:

| Input | Batch | CPU native ms | CUDA native ms | CPU e2e ms | CUDA e2e ms | e2e CPU/CUDA |
|---|---:|---:|---:|---:|---:|---:|
| ALOHA 640×480 AV1 | 1 | 50.0 | 41.5 | 99.7 | 46.4 | 2.15× |
| ALOHA | 8 | 45.9 | 30.5 | 63.5 | 34.6 | 1.84× |
| ALOHA | 32 | 47.4 | 31.5 | 62.1 | 35.6 | 1.75× |
| AgiBot 640×528 AV1 | 1 | 108.6 | 89.0 | 152.4 | 93.4 | 1.63× |
| AgiBot | 8 | 100.8 | 73.6 | 119.6 | 78.3 | 1.53× |
| AgiBot | 32 | 113.2 | 66.8 | 129.8 | 71.2 | 1.82× |

Decoder creation was ~30–33 ms in both devices. The recorded first decode was
1.5–6.4 ms on CPU but 34–44 ms on CUDA; it is the first call in this process
after correctness/CUDA work, not a cold-process or NVDEC-initialization
measurement. It is outside the warm timings. VRAM allocated
peaked at 4.4–35.8 MiB (reserved 24–86 MiB); process RSS was dominated by
reference frames (~1.4 GiB). `nvidia-smi` sampled 21–28% NVDEC utilisation after
the timed groups (short runs can under-sample; this is auxiliary evidence only).

The result is a real microbenchmark benefit for this workload, not just a bare
decode ratio. It does not establish a benefit for full LeRobot windows, action
padding, multi-camera batches or DataLoader workers, and it does not prove
RGB-equivalent output. The public claim is limited to the measured microbenchmark.

### 4.5 Packaging

The wheel (323 KiB, 29 files) contains `environment.py`, `gpu_metrics.py` and the
bundled fixture. A fresh `.wheel-check` environment installed the wheel with
`[repair]`, imported the auxiliary modules without numpy, ran the offline demo,
and passed 26/26 single-phase conformance checks. GPU dependencies remain in
the consumer; they are not runtime dependencies of the audit package.

## 5. Repository changes

- Measured host/timezone, source commit, consumer versions and separate
  requested/observed decode devices in real-data and sampling reports.
- Preserved venv interpreter symlinks instead of resolving them to the base
  interpreter; this fixed a Linux-only validation failure.
- Added the standalone benchmark with explicit `unavailable`/CPU-fallback
  handling, bounded references, marker identity, two references for real video,
  raw and range-adjusted RGB metrics, and native/common-endpoint/end-to-end
  timings.
- Added regression tests for environment reporting, interpreter paths, colour
  range metrics and exact/wrong/ambiguous frame decisions.
- Found and fixed two benchmark-reporting issues during the runs: fault
  fixtures are now judged by detected identities rather than unrelated passes,
  and WSL `nvidia-smi` is found outside PATH (including `/usr/lib/wsl/lib`).

The experiment prompts a benchmark design change, not a default reader change:
GPU decode is not wired into `probe-loader` or LeRobot, because real-data
identity coverage is still partial and pixel equality is not established.

## 6. Limitations and non-claims

- WSL2, one RTX 4090, one driver and one software stack; not bare-metal Linux.
- Two real samples, both AV1 and 640-wide; small H.264 fixtures are synthetic.
- No GPU DataLoader workers, no fork-inherited CUDA context, no multi-GPU.
- No full LeRobot GPU-reader adapter; no stock-reader GPU claim.
- No physical synchronization proof, no training/robot-success claim, no
  natural-defect claim, and no dataset-wide identity certification.
- Five timed samples per group; no p95. Results are medians of a short run and
  should not be generalized to other codecs, resolutions or request plans.
- CUDA RGB is not pixel-identical; the TV-range adjustment is reported, not
  silently applied to turn failures into passes.
- The current CPU audit install remains the default and is still the only
  supported end-to-end path.
